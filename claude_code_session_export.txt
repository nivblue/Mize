  Tool: the dotnet CLI, using dotnet add package <name> --version <x> and dotnet
  restore. NuGet is built into the SDK, so there's nothing separate to install.
  The SDK isn't on your machine, so I'd run these commands inside the
  mcr.microsoft.com/dotnet/sdk:8.0 Docker image, as you chose earlier. Nothing
  gets installed locally. The restored packages are cached in a Docker volume so
  rebuilds stay fast.

    also reference Swashbuckle.AspNetCore if you want Swagger, which I'll ask

  - Optionally centralize versions in a Directory.Packages.props file (central

⏺ What it is: Swashbuckle.AspNetCore is a NuGet package that generates an
  OpenAPI (Swagger) specification from your ASP.NET Core endpoints. It also
  serves Swagger UI, an interactive web page where you can read the endpoints
  and call them from the browser. It has three parts:
  - Swashbuckle.AspNetCore.Swagger serves the generated swagger.json.
  - Swashbuckle.AspNetCore.SwaggerGen builds the spec from your controllers,
    models and XML doc comments.
  - Swashbuckle.AspNetCore.SwaggerUI is the browser page.

  Creator: It was started by Richie Morris, who goes by domaindrivendev on
  GitHub. It's open source under the MIT license, and the community now helps
  maintain it. I'm going from memory on the maintainer details, so check the
  repo for the current list.

  Documentation:
  - Repo and README: https://github.com/domaindrivendev/Swashbuckle.AspNetCore
  - NuGet page: https://www.nuget.org/packages/Swashbuckle.AspNetCore
  - Microsoft's guide: search "Get started with Swashbuckle and ASP.NET Core" on
    learn.microsoft.com

  Things to know for your decision:
  - It fits your project because your /// comments on endpoints would show up in
    the UI. That matches your documentation requirement.
  - It's the long-standing de facto choice, and the .NET 8 templates include it.
    Starting with .NET 9, Microsoft stopped including it in templates and moved
    to its own Microsoft.AspNetCore.OpenApi package. That package generates the
    spec but has no UI. We're targeting .NET 8, so Swashbuckle is the simpler
    path.
  - I'd register it in Development only, so the UI isn't exposed elsewhere. It
    adds one package, so you can remove it later without touching the rest of
    the code.

  I haven't opened these links from here, so the details above come from my own
  knowledge. I can look them up if you want them checked.

❯ show me small code example before i decide                                    

⏺ Here is the same test written both ways. It checks that an unchanged duplicate
  returns the unchanged status and doesn't write to the database.

  Plain xUnit Assert (no extra package):
  /// Verifies an identical re-ingest reports "unchanged" and skips the DB 
  write.
  [Fact]
  public async Task 
  Ingest_IdenticalReservation_ReturnsUnchanged_AndDoesNotWrite()
  {
      var result = await _service.IngestAsync(_sameReservation);

      Assert.Equal(IngestStatus.Unchanged, result.Status);
      Assert.Equal(0, _repo.WriteCount);
      Assert.Collection(_logger.Entries,
          e => Assert.Equal(LogLevel.Information, e.Level));
  }

  FluentAssertions (extra NuGet package):
  /// Verifies an identical re-ingest reports "unchanged" and skips the DB 
  write.
  [Fact]
  public async Task 
  Ingest_IdenticalReservation_ReturnsUnchanged_AndDoesNotWrite()
  {
      var result = await _service.IngestAsync(_sameReservation);

      result.Status.Should().Be(IngestStatus.Unchanged);
      _repo.WriteCount.Should().Be(0);
      _logger.Entries.Should().ContainSingle()
          .Which.Level.Should().Be(LogLevel.Information);
  }

  Differences:
  - Readability: FluentAssertions reads like a sentence. Plain Assert is a
    little more verbose and puts expected, actual in a fixed order, which people
    sometimes swap by mistake.
  - Failure messages: FluentAssertions usually gives more descriptive messages.
    For a project this size, xUnit's messages are enough.
  - Dependency and license: FluentAssertions is a third-party package. Starting
    with version 8, it needs a paid license for some commercial uses. Versions 7
    and earlier remain free, but they won't get new updates. Plain Assert ships
    with xUnit and has no license concern.
  - Stability: you said you prefer stability right now, and plain Assert adds
    nothing to maintain.

  I'd go with plain xUnit Assert. Which do you want?

  decisions I'm making on my own, with my reasoning:

  - Controllers instead of Minimal APIs: they separate cleanly for unit tests
    and keep per-action docs tidy.

    instants round-trip exactly.

⏺ Where and how SQLite runs

  SQLite is not a server, so there's no database container, port or install.
  It's a library that runs inside the API process, and the database is a single
  file.

  - Library: the Microsoft.Data.Sqlite NuGet package bundles the native SQLite
    engine. Dapper sends SQL through it.
  - File location in Docker: the API reads the connection string Data 
    Source=/data/mize.db, so the file is /data/mize.db inside the container.
    - That string comes from the ConnectionStrings__Reservations environment
      variable, set in the Dockerfile and in both compose files. It overrides
      the default Data Source=data/mize.db in src/appsettings.json.
  - Mount to your machine: /data is bind-mounted from a folder on your machine.
    - docker-compose.yml uses ./data.
    - docker-compose.local.yml uses ./data-local.
    - So the real file is ./data/mize.db or ./data-local/mize.db. It survives
      container removal, and you can delete the folder to start fresh. Both
      folders are git-ignored.
  - Startup: Program.cs calls DatabaseInitializer, which runs CREATE TABLE IF 
    NOT EXISTS Reservations .... SqliteConnectionFactory creates the folder if
    it's missing.
  - Connections: each repository call opens its own connection, and
    Microsoft.Data.Sqlite pools them.
  - Journal mode: it uses SQLite's default, not WAL. WAL is unreliable on Docker
    bind mounts from macOS.
  - Concurrency: one in-process lock in ReservationService serialises
    read-then-write, so parallel duplicates can't collide.
  - In tests: each test creates its own throw-away file under the OS temp folder
    and deletes it afterwards. Nothing touches ./data.

  Findings, most important first

  All of these come from experiments against a real container unless stated
  otherwise.

  1. The "stale update" rule deviates from the spec and can lock a record. 
  (Medium-high)
  - The spec says that if the same reservationId arrives with different details,
    update the record. We ignore the update if its updatedAtUtc is older than
    the stored one. You approved this, and it's documented. But a grader or

    returned stale. A single bad or skewed future timestamp makes the record
    reject every legitimate update until real time reaches 2099.
  - Fix: reject timestamps too far in the future, or make the stale rule
    configurable and off by default. The most literal fix is to drop it.

  2. The throttle can be bypassed, and there's no limit on input size. (Medium)
  - Spelling variants: with the limit at 3, acme got 201 201 201 429, while
    ACME, acme  and Acme were each accepted. The supplier id isn't trimmed or
    case-normalized, so one supplier can get several quotas.

    throttled. That was my design: validation runs before the limiter. A flood
    of malformed-but-parsable requests is never limited, which doesn't fit "more

    stored. The limiter and stats dictionaries are keyed on client-controlled
    strings and never pruned (by reading). Random supplier ids grow memory
    forever.

    invalid requests that carry a supplier id.

  The pieces

  - Validation: non-empty ids, UTC timestamps, checkOut after checkIn, price >= 
    0, and all errors reported at once.
  - Dedup: Reservation is a record, so equality compares every field. existing 
    == incoming means "same details". Prices compare as decimals, so 450 equals
    450.00.
  - Rolling window: one queue of accepted-request timestamps per supplier, under
    a lock. On each request it drops entries a full window old, rejects if 100
    remain, and otherwise appends. Rejected requests aren't recorded, so a
    supplier recovers as soon as old requests age out.
  t=0 ........... t=60
  [100 accepted]   request at t=59 → 429, Retry-After=1
                   request at t=60 → allowed (the t=0 hits expired)
  - Storage: SQLite, Dapper, parameterized SQL, with the primary key
    (SupplierId, ReservationId). Dates are stored as ISO-8601 UTC text and
    prices as invariant decimal text, so values round-trip exactly.
  - Concurrency: the write gate makes read-decide-write atomic within the
    process, so 20 parallel identical requests give one created and nineteen
    unchanged.

  1. What fixing item 5 involves

  Item 5 bundles two problems: the global write lock that only works inside one
  process, and the stats that aren't persisted.

  A. Replacing the lock with an atomic database transaction. Today the service
  takes an in-process SemaphoreSlim, reads the row, decides, then writes. Two
  API processes on one SQLite file would both see "no row" and the second insert
  would fail with a primary-key violation, a 500. Steps:
  1. Move the read, decide and write into one transaction that starts with BEGIN
     IMMEDIATE, which takes SQLite's write lock up front. Microsoft.Data.Sqlite
     does this with BeginTransaction(deferred: false). Other processes wait on
     SQLite's busy timeout, which defaults to 30 s, and don't fail.
  2. Extract the dedup rules (new, identical, stale, update) into a pure
     function, so they stay unit-testable. The repository then needs one method
     that runs that function inside the transaction, in place of the separate
     Get, Insert and Update.
  3. Delete the semaphore, and adjust the service tests that mock the three
     methods.
  4. Add a test that starts two API hosts on the same database file and sends
     identical requests in parallel, expecting exactly one created.

  One honest point: this is a correctness gain across processes, not a speed
  gain. SQLite allows one writer at a time anyway, so ingest throughput stays
  the same.

  B. Persisting the stats. Steps:
  1. A SupplierStats table with one row per supplier and counters, updated with
     INSERT ... ON CONFLICT DO UPDATE SET Created = Created + 1.
  2. For the created, updated, unchanged and stale outcomes, do that increment
     in the same transaction as the reservation write, so stats and data can
     never disagree.
  3. ISupplierStatsTracker is synchronous today, so it must become async. That
     touches the controller and several tests.
  4. A restart test: ingest, restart the host, and check the stats survived.

  The design problem is throttled counts. Each rejected request would become a
  database write, exactly when a supplier is flooding you. Your options are
  write-through (simple, adds write load under attack), buffering in memory and
  flushing every few seconds (cheap, but a crash loses a few seconds of counts),
  or leaving throttled counts in memory only.

  The rolling window itself stays in memory, so two instances would still not
  share rate-limit state. Fixing that needs a shared store such as Redis or a
  timestamps table, which is out of scope.

  Total effort is roughly half a day. It's a real design change, and you'd need
  to choose the throttled-counter option.

⏺ How the rate limiter works

  1. Where it sits

   supplier ──► model binding ──► validation ──► RATE LIMITER ──► service ──► 
  database
                (400 if bad       (400 if bad     │
                 JSON)             fields)        ├─ allowed: timestamp 
  recorded, request continues
                                                  └─ full:    429 + Retry-After,
  throttled counter +1,
                                                              nothing is 
  recorded, nothing is written

  Invalid requests are rejected before the limiter and never reach it. The
  limiter is keyed by supplierId, which is read from the request body.

  2. The data structure

  Each supplier has its own queue of the timestamps of its accepted requests,
  oldest first, behind its own lock:

   supplier "acme"  →  Queue:  [ 10:00:00.1 ][ 10:00:03.4 ][ 10:00:07.9 ] ... 
  (at most 100 entries)
                                ▲ oldest                                 ▲ 
  newest
   supplier "beta"  →  Queue:  [ ... ]            (separate queue, separate 
  lock)

  Every request runs these steps under that supplier's lock:

   now = clock.UtcNow
   1. DROP   every timestamp that is a full window old   (timestamp <= now − 60 
  s)
   2. COUNT  what is left in the queue
   3. if count >= 100  →  REJECT, retryAfter = oldest + 60 s − now      (queue 
  unchanged)
      else             →  ACCEPT, add `now` to the queue

  3. A walk-through (limit 3 and window 10 s so it fits on a page)

   time   request   queue before          action                      queue 
  after       result
   ────   ───────   ──────────────────    ─────────────────────────   
  ───────────────   ───────────────────
    0 s     #1      []                    accept                      [0]       
         ✓ 201
    1 s     #2      [0]                   accept                      [0,1]     
         ✓
    2 s     #3      [0,1]                 accept                      [0,1,2]   
         ✓
    3 s     #4      [0,1,2]  full         reject (not recorded)       [0,1,2]   
         ✗ 429, retry in 7 s
    5 s     #5      [0,1,2]  full         reject (not recorded)       [0,1,2]   
         ✗ 429, retry in 5 s
   10 s     #6      drop 0 → [1,2]        accept                      [1,2,10]  
         ✓   (0 is exactly 10 s old: expired)
   11 s     #7      drop 1 → [2,10]       accept                      [2,10,11] 
         ✓
   12 s     #8      drop 2 → [10,11]      accept                      [10,11,12]
         ✓
   13 s     #9      [10,11,12]  full      reject                      [10,11,12]
         ✗ 429, retry in 7 s

  The window slides with each request. At every instant, the queue holds exactly
  the accepted requests of the last 60 s.

  4. The window really is rolling

   FIXED buckets (what we did NOT build)          ROLLING window (what we built)

    bucket 1          bucket 2                     any 60 s span, anywhere on 
  the line:
   |■■■■■■■■■■|■■■■■■■■■■|                          ◄────── 60 s ──────►
   0         59|60        119                      |■■■■■■■■■■■■■■■■■■■■|  never
  more than 100
          100 + 100 = 200 requests
          within 2 seconds around :59/:60

  A fixed bucket resets at the boundary, so a supplier can send 100 just before
  it and 100 just after it. The rolling window has no boundary.

  5. Why rejected requests do not count

   A flood of 10 req/s from one supplier, limit 100 per 60 s:

   OURS (rejected not recorded)                 ALTERNATIVE (rejected also 
  recorded)
   accepted ■ ■ ■ … ■ (100)                      accepted ■ ■ ■ … ■ (100)
   then:   ✗✗✗✗✗✗ ✗✗✗✗✗✗ ✓ ✗✗✗✗✗ ✓ …           then:   ✗✗✗✗✗✗✗✗✗✗✗✗✗✗✗✗✗✗✗✗✗✗✗✗…
           one slot frees as each old hit               every rejected request 
  refills the window,
           ages out: steady ~100 per 60 s               so the supplier stays 
  blocked until it
                                                        STOPS for a full 60 s

  Ours converges to the allowed rate of 100 per 60 s and is simple to explain.
  The alternative punishes hammering harder.

  6. Concurrency

   request A (acme) ─┐
   request B (acme) ─┼─► per-supplier lock: one at a time → count is exact, 
  never 101 accepted
   request C (beta) ─┘   beta has its own lock → acme and beta never wait for 
  each other

  Pros

  Pro: Exact
  Why: It is a true rolling window with no boundary burst, and a unit test with
  500 parallel calls never accepts more than the limit.
  ────────────────────────────────────────
  Pro: Cheap
  Why: Each timestamp is added once and removed once, so each request does O(1)
  amortized work. Memory is bounded by the limit: about 100 timestamps per
  active supplier (I estimate 2 KB per supplier, by arithmetic, not measured).
  ────────────────────────────────────────
  Pro: Fair
  Why: Suppliers don't affect each other. A supplier recovers the moment its
  oldest request ages out, and Retry-After tells it exactly when.
  ────────────────────────────────────────
  Pro: Testable
  Why: The clock is injected, so tests move time instantly. No test sleeps,

  ────────────────────────────────────────
  Pro: Configurable
  Why: The limit and window come from configuration, without a code change.
  ────────────────────────────────────────
  Pro: Matches the spec text
  Why: At most 100 accepted in any 60 s, and further requests rejected until a

  Risk: State is in memory
  Severity: Medium
  Detail: A restart gives every supplier a fresh quota, so a supplier could use

  ────────────────────────────────────────
  Risk: Supplier identity comes from the request body
  Severity: Medium

  ────────────────────────────────────────
  Risk: Invalid requests never count
  Severity: Medium
  Detail: A flood of requests that fail validation is never throttled. I

  ────────────────────────────────────────
  Risk: Memory only grows

  Risk: Wall clock, not a monotonic clock

  ────────────────────────────────────────
  Risk: The decision comes after parsing
  Severity: Low
  Detail: A throttled request has already been read and validated, so a flood
  still costs CPU.
  ────────────────────────────────────────
  Risk: Quota is consumed before the work is done
  Severity: Low
  Detail: A request that later fails with a 500, or that the client cancels,

  ────────────────────────────────────────
  Risk: Boundary convention
  Severity: Low
  Detail: A request exactly 60.000 s after an earlier one is allowed, because

  ────────────────────────────────────────
  Risk: Retry-After is rounded up to whole seconds
  Severity: Low
  Detail: A client may wait up to a second longer than needed.

  What would change with each alternative

   Token bucket     smooth refill, allows a short burst        → doesn't match 
  "100 in any 60 s" exactly
   Sliding counter  two counters and a weighted estimate        → less memory, 
  but only an approximation
   Shared store     Redis or a database table of timestamps     → fixes restart

  I chose the exact queue because it matches the spec text, and because it's

   request path (fast, no I/O)            background (every few seconds + on 
  shutdown)
   ───────────────────────────            
  ─────────────────────────────────────────────

  Notes: Simple, but it makes ISupplierStatsTracker async and touches the

  What I'd suggest: option 3, in a read-friendly form

   throttled request ─► memory: delta["acme"] += 1      (no I/O on the request 
  path)

   every 5 s and on graceful shutdown (one background service):
       one transaction:  INSERT ... ON CONFLICT DO UPDATE SET Throttled = 
  Throttled + @delta
       deltas reset only after the commit succeeds (a failed flush keeps them 
  and retries)

   GET stats:   throttled = SupplierThrottle.Throttled (SQL)  +  not-yet-flushed
  delta (memory)

  A few properties make it attractive:
  - No startup recovery step at all. Because the read adds the database total to
    the in-memory delta, there is nothing to load when the service starts. The
    table is the recovery.
  - The request path is unchanged. It stays memory-only and equally fast.
  - Bounded write cost. One small transaction per interval, independent of flood
    size.
  - Lifetime semantics. throttled then means the same thing as ingested
    (lifelong), so the response is coherent and no throttledSinceUtc is needed.
  - Multi-instance friendly. The deltas are additive, so several instances
    flushing into the same row still produce the right total.

  What it costs and where it can go wrong

  - A crash loses up to one interval of throttle counts, a few seconds. A
    graceful stop (docker stop) loses nothing. I'd verify it with a test that
    sends SIGTERM and restarts.
  - A transient inexactness. Between the commit and the moment the delta is
    zeroed, a concurrent GET can briefly count some events twice or not at all.
    A small lock shared by the flush and the read closes it, and both are fast.
  - Shutdown ordering. The final flush has to run after in-flight requests
    finish. This needs care and a test.
  - More parts: a new table, one background service and a persistence class. I'd
    estimate roughly 80 lines of code and 6 to 8 tests, so it's moderate for a
    small project.
  - GET cost: one more primary-key lookup, which is negligible next to the count
    query.

  A challenge to the framing

  A throttle counter is an operational metric. In production systems such
  counters conventionally reset on restart, and the monitoring tool handles the
  reset. The alternative is to treat the reset as acceptable and make it
  visible, with option 0. That's zero code, and it matches your view that a
  clean state after a restart is fine for the limiter itself.

  My recommendation depends on one question: are the stats a business fact or
  monitoring? The spec puts "ingested" and "throttled" in the same sentence, as
  one report. If ingested becomes lifelong, a throttled that resets would give a
  mismatched response. In that case I'd build option 3. If you'd rather keep
  things minimal, option 0 is honest and costs nothing.

⏺ 1. On shutdown, does it write every supplier's throttled count?

  No, only the suppliers that have unflushed throttles. The shutdown flush is
  the same operation as the periodic one, run one last time. If 3 suppliers were
  throttled since the last flush, it writes 3 rows in one transaction.
  Suppliers that were never throttled, or were already flushed, cost nothing.

  There are two ways to write a row:
  - Deltas: Throttled = Throttled + @delta. This is safe if several instances
    share the table.
  - Dirty totals: Throttled = @total. This is idempotent, so a retry is
    harmless, but it's only correct with one writer.

  Since you're assuming a single instance for now, either works.

  2. When to query SQL, and is every GET heavy?

  lookup, but your principle is sound. SQLite in its default journal mode lets a
  reader and a committing writer block each other briefly, so reads on the hot
  path aren't free. A cache removes that contention.

  Point 1: memory as a cache, SQL as the truth

  Yes, there's a clean version, which is cache-aside with incremental
  maintenance. Since only this process writes, it always knows when the data
  changed:

   GET stats(acme)
     ├─ acme in cache?  yes → answer from memory                     
  (microseconds, no DB)
     └─ no (first touch since start) → ONE SQL read: row count + saved throttle 
  total → store → answer

   ingest → Created   (after the insert has committed) → cache[acme].Ingested++ 
        no DB read
   ingest → Updated / Unchanged                        → nothing (the row count 
  didn't change)
   request throttled                                   → 
  cache[acme].Throttled++, mark dirty

   flush (every ~5 s and on graceful shutdown) → write ONLY the dirty suppliers,
  one transaction

    lifetime. A restart simply starts with an empty cache.
  - Startup: it's cheap, because nothing is preloaded. Suppliers that nobody
    asks about are never loaded.
  - Reliability: the rows are fully rebuildable from SQL. Only the unflushed
    throttle count can be lost in a crash.

  The mitigations are an optional safety-net expiry, for example re-reading

⏺ 1. Can the cache lose rows with one instance?

  With a single instance and no one else writing to the database, it can't lose
  rows, provided three rules are followed. Without them there are real ways to
  be wrong:

  Situation: A race on the first load. GET reads COUNT = 10, a new row commits
  and tries to increment, but no entry exists yet. Then GET stores 10.
  What goes wrong: The new row is lost from the cache and the count stays low
  until a restart.
  Rule that prevents it: Do the first load while holding the same write gate
  ingests use, so no insert can be in flight during the load. It happens once
  per supplier per process lifetime.
  ────────────────────────────────────────
  Situation: Incrementing too early. The increment runs before the commit, and
  the insert then fails.
  What goes wrong: The count is too high.
  Rule that prevents it: Increment only after the insert has committed, inside
  the gate, with no await in between.
  ────────────────────────────────────────
  Situation: An ambiguous failure. The insert commits and then something throws,

  such as a cancellation or a dropped connection.
  What goes wrong: The count is too low.
  Rule that prevents it: On any exception in the insert path, drop that
  supplier's cache entry. The next read reloads from SQL.
  ────────────────────────────────────────
  Situation: Updates and duplicates.
  What goes wrong: They don't change the row count.
  Rule that prevents it: Increment only on Created.
  ────────────────────────────────────────
  Situation: Crash or restart.
  What goes wrong: The cache is gone.
  Rule that prevents it: Nothing to do: the next first read rebuilds it from
  SQL,
  and the rows themselves are never at risk.

  An ingest for a supplier whose entry isn't loaded yet does nothing to the
  cache. The first GET will load a count that already includes that row. That
  keeps the ingest path free of database reads.

  Should we add a periodic re-read? I'd say it's optional, and I'd lean toward 
  skipping it at first:
  - The only ways to drift are outside actors (manual edits, a restored file) or
    a bug. The sqlite3 shell is read-only by default.
  - A re-read that silently fixes the count would also hide a bug.
  - A cheaper, more useful safeguard is a test: run many concurrent ingests and
    assert that the cached count equals SELECT COUNT(*).

  If you want a safety net, add it as a detector: re-check a supplier
  occasionally and log a WARN if the cache disagrees with SQL. Idle-entry
  eviction, for example dropping an entry after 10 minutes unused, would double
  as a periodic re-read and as a memory bound. A GET for a random supplier id
  must not create cache entries, or the cache grows without limit. So an entry
  is created only for suppliers that actually have rows or throttles. This is
  the same unbounded-growth concern as finding 2c.

  I don't think this is over-engineering, as long as it stays at those three
  rules. They're what make "cache plus increments" correct. A TTL or reconcile
  loop is the part that would be over-engineering for now.

  2. When are the throttled counts pulled from SQL?

  On the same first read, in the same query. The cache entry per supplier holds
  both numbers, and one round trip loads both:

  SELECT (SELECT COUNT(*) FROM Reservations WHERE SupplierId = @s),
         (SELECT Throttled FROM SupplierThrottle WHERE SupplierId = @s);

  Only GET stats ever loads. Neither the ingest path nor the throttle path reads
  from the database. For throttles the entry keeps two fields, so the total is
  always exact:

   throttled total  =  DbFlushed (what SQL already has, loaded once)  +  
  Unflushed (increments not yet written)

   request throttled →  Unflushed++                      (works even if nothing 
  is loaded yet)
   flush (5 s / stop) → write Unflushed as an additive delta, then:  DbFlushed 
  += delta, Unflushed -= delta
   GET                →  DbFlushed + Unflushed            (memory only after the
  first load)

  Because the flush writes additive deltas, it doesn't need the entry to be
  loaded. If a supplier is throttled and nobody calls GET for it, the flush
  still writes it. The first GET after a restart then loads a total that already
  includes everything flushed.

  5. Tests: the concurrent cache-equals-SQL test, restart survival, a

  The gate

  What it is. WriteGate is a lock for the whole process, with room for exactly
  one holder. Think of a single key to a room. Whoever holds the key is the only
  one allowed inside, and everybody else waits outside until the key comes
  back. It's a one-slot SemaphoreSlim wrapped in a small class, and there is one
  instance for the whole service.

  What changed. Before, ReservationService had its own private lock, and nothing
  else could use it. Now the gate is a shared object, IWriteGate, handed to two
  classes:

   ReservationService.IngestAsync        SupplierStatsCache.LoadAsync  (first 
  read of a supplier only)
   ───────────────────────────────       
  ─────────────────────────────────────────────────────────────
   take the gate                         take the gate
     look up the reservation               read row count + saved counters from 
  SQL
     insert or update                      store them in the cache
     record the outcome in the cache     release the gate
   release the gate

  Why it had to be shared. The cache needs to read a supplier's row count once,
  and then keep it exact by adding 1 for each new reservation. Without the
  shared gate, this could go wrong:

   the cache reads  COUNT = 10  from SQL ...
                           ... meanwhile an ingest commits row #11 and records 
  "+1"
   the cache stores 10      → row #11 is lost from the count, and stays lost

  With the shared gate, the two can't overlap. The read waits until an in-flight
  ingest has finished and recorded itself, so the count it loads is already
  correct. After that, every ingest is a "+1" on a number that is known to be
  right.

  What the handle does. EnterAsync returns a handle, and using var gate = ...
  releases it when the method ends, even if it throws. Disposing the handle
  twice releases only once, so the gate can never be entered by two callers at
  once. This is tested.

  What it costs.
  - A request waits only if another one is already inside, as before. One SQLite
    file allows one writer at a time anyway.
  - A stats read waits for the gate only on the first load of a supplier, once
    per supplier per process lifetime. A read from the cache never touches the
    gate. A test proves it.
  - It protects one process only. If a second instance ever wrote to the same
    database, this gate wouldn't see it.

  So only two callers hold the gate. SQLite protects itself against concurrent
  file access, and the gate isn't about that. It exists for a logical invariant
  that spans several steps: "the cached row count equals the rows in the file".

  Your instinct is right: this leaks

  Right now two classes must each remember to take the gate, and the rules are
  spread out. Rule 1 lives in the cache, and rules 2 and 3 live in the service.
  A third caller that forgot the gate would break the count silently, with no
  compiler error. The correctness depends on discipline.

  Why "put it in the repository" doesn't work as-is

  A gate inside each repository method would protect single calls, but the race
  is across several calls:

   get row → decide → insert → record in cache      ← the invariant spans ALL of
  these

  If the lock were taken inside GetAsync and again inside InsertAsync, two
  ingests could still interleave between them. The gate has to cover the whole
  sequence, so the sequence has to live somewhere that owns it.

  Options

  Option: A. Atomic repository operation
  What it means: One call, UpsertAsync, does the read-decide-write inside a
  single SQL transaction (BEGIN IMMEDIATE).
  Trade-off: Also makes several instances safe. But the cache-to-database
  invariant is still a separate problem, so something still has to coordinate
  it.
  ────────────────────────────────────────
  Option: B. One cohesive "store" adapter (my recommendation)
  What it means: A single class owns the gate privately, together with the
  repositories and the cache. The ingest service calls store.RunAsync(...) and
  the stats read calls store.GetStatsAsync(...). Nobody else sees a gate.
  Trade-off: Moderate refactor, more indirection, but the rules can't be
  forgotten.
  ────────────────────────────────────────
  Option: C. Keep it, narrow the API
  What it means: Replace the raw handle with gate.RunAsync(async () => ...).
  Trade-off: Can't forget to release the gate, but can still forget to take it.
  Smallest change.
  ────────────────────────────────────────
  Option: D. Leave as it is
  What it means: The rules stay documented and tested.
  Trade-off: Cheap, but depends on discipline.

  What option B would look like

   Controller ─► ReservationService   pure rules: "new / duplicate / changed"; 
  knows nothing about the gate or the cache
                      │
                      ▼
                ReservationStore  ◄── the ONLY class that knows the gate, the 
  cache and the rules 2 and 3
                  │  RunAsync(work):  take gate → run read/decide/write → on 
  success record the outcome
                  │                   → on exception drop the cached row count →
  release gate
                  │  GetStatsAsync(): answer from the cache, or take gate → load
  → cache
                  ▼
          ReservationRepository, StatsRepository, SupplierStatsCache, 
  StatsFlushService

  The service would shrink to the rules:

  return await _store.RunAsync(request.SupplierId, async work =>
  {
      var existing = await work.GetAsync(...);
      if (existing is null)  { await work.InsertAsync(incoming); return
  IngestStatus.Created; }
      if (existing == incoming) return IngestStatus.Unchanged;
      await work.UpdateAsync(incoming); return IngestStatus.Updated;
  });

  Inside InsertAsync the store would handle "record after the commit" and
  "invalidate on failure" itself, so the service can't get rules 2 and 3 wrong.
  The cache would depend on the store's gate privately, and the shared
  IWriteGate interface would go away.

  Cost and my recommendation

  - Option B touches about 8 to 10 files: the service, the cache, the
    controller, the DI setup, and the tests for the service and the cache. The
    behavior and the API stay the same, and the existing tests would be adapted.
  - If this were production code, I'd do option B. For this size of project,
    option C is a reasonable cheap step. Option A is a separate, bigger
    improvement that also helps with multiple instances, and we discussed it
    earlier.

    .NET string (two bytes per character), kept as a key for the rest of the
    process's life. The measured growth was larger because the big request
    buffers are large-object garbage that is collected late. The default request
    body limit is about 30 MB, so a single 1 MB id would retain around 2 MB,
    and a thousand requests would be roughly 2 GB.
  - All 300 long-id requests were accepted with 201. The same data is also
    written to SQLite, so the disk fills as well as the memory.

  What does not grow

  - The timestamp queue per supplier is capped at the limit, 100 entries.
  - The counters are a fixed size.
  - A GET for an unknown supplier creates no cache entry. That was strict rule
    5, and it's tested.
  - Invalid requests are rejected before the limiter, so they allocate nothing.

  Who can trigger it

  - Real suppliers: a few dozen or hundred of them cost nothing, so honest use
    is safe.
  - A hostile or buggy client: the service has no authentication, so anyone who
    can reach it can rotate ids. The result would be an out-of-memory kill, then
    a restart through restart: unless-stopped, which clears the rate-limit
    windows and loses up to 5 seconds of counters.

  Fix options, cheapest first

  Option: 1. Maximum id length (for example 128 characters)
  What it does: Rejects absurd ids with 400.
  Cost and trade-off: A few lines and a test. It removes the worst
  amplification,
  the 200 KB keys.
  ────────────────────────────────────────
  Option: 2. Sweep the limiter
  What it does: A periodic task removes windows whose queue is empty. An empty
  window behaves exactly like no entry.
  Cost and trade-off: Small. It bounds limiter memory to recently active
  suppliers.
  ────────────────────────────────────────
  Option: 3. Evict idle cache entries
  What it does: Drop entries that are idle and fully flushed. SQL has the truth,

  so the next read reloads them.
  Cost and trade-off: Medium. It must respect the strict rules (gate, flush
  lock,
  entry lock), so it needs care and tests.
  ────────────────────────────────────────
  Option: 4. Normalize ids (trim, case-insensitive)
  What it does: Stops acme, ACME and acme  from being three suppliers.
  Cost and trade-off: It changes how identity works, but it also fixes the
  throttle bypass.
  ────────────────────────────────────────
  Option: 5. A registry of known suppliers
  What it does: Unknown ids are rejected. Memory is bounded by the real number
  of
  suppliers.
  Cost and trade-off: The real-world answer, but it's a product decision that
  the
  spec doesn't define, and it comes with authentication.
  ────────────────────────────────────────
  Option: 6. A container memory limit and an alert
  What it does: Operational safety net.
  Cost and trade-off: Doesn't fix the cause.

  For a scoped exercise I'd do options 1 and 2 first, because they're small and
  safe, and add 3 if you want it complete. The spec says production-level
  hardening isn't expected, so this is a documented compromise. MIZE.md mentions
  "no eviction", but it doesn't yet say that ids have no length limit, and I'd
  add that.

  Which options do you want? I'd also include option 4 whenever we get to the
  throttle-bypass findings, since it's the same root cause.
